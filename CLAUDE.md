# CLAUDE.md

Context for AI assistants (Claude Code etc.) working in this repo. Read this first. The README
explains the design for reviewers; `analyses/FINDINGS.md` holds the profiling evidence;
`ai/planning_log.md` records every decision and change of direction.

## What this project is
A dbt project on BigQuery that turns mock pupil activity into a KS2 SATs-style scaled score
(80–120) for Maths and English, plus % correct for every assessed subject, recomputable as at any
date, in one flat row per pupil for the app database. It is a take-home task for Atom; **the
reasoning matters more than the result**, so every non-obvious decision is written down (README,
FINDINGS, or a SQL comment).

## Working rules
- **Never run `dbt`, `gcloud` or `bq` commands (including dry runs and `scripts/run_analyses.py`)
  without the user's permission.** Write the code, then give the user the command to run.
- **No custom macros without the user's permission**; keep SQL readable.
- Keep README, FINDINGS, PLAN.md and this file in step with the code; append decisions to
  `ai/planning_log.md` as they're made.
- Commit in small, descriptive steps; don't squash (the history is evidence). Commit only when asked.
- Fix failing tests rather than loosening them; if a test is loosened, say why in the yml.

## Stack
- **dbt Core 1.12.6** + **dbt-bigquery 1.12.1**, Python 3.12, managed by **uv** (`pyproject.toml`,
  `uv.lock`). Run everything through uv (`uv run dbt ...`); add dependencies with `uv add`.
  Packages: `dbt_utils` (tests only). Dev: `sqlfluff`.
- **BigQuery:** project `atom-analytics-candidates`, location `europe-west2`. Source dataset
  `de_raw` (read only). Everything is built in `james_oakley` (the profile's dataset); never set
  `+schema`, or dbt creates `james_oakley_<schema>`.
- **Auth:** OAuth via gcloud; `profiles.yml` in `~/.dbt/`, never committed.
- **Point-in-time:** `dbt build --vars '{as_at: "YYYY-MM-DD"}'`; no `as_at` = all data.

## Layout

## SQL conventions
- **SQLFluff** enforces style: run `uv run sqlfluff fix models tests analyses`, then `lint`, after
  any SQL change. It uses the Jinja templater with dbt builtins, so it runs locally without dbt or
  BigQuery. **Keywords, functions, literals and types in CAPITALS; names lowercase.** Column
  aliases aligned within each select; explicit `AS` for tables and columns.
- **No `SELECT *` or `t.*`**: always list the columns.
- **As simple as possible:** a plain select with joins when one query does the job; a CTE only
  for a step that needs its own query (an aggregate to join on, a `QUALIFY` pick). No
  pass-through or `final` CTEs. Avoid cross joins.
- Reference tables only through `{{ ref() }}` / `{{ source('de_raw', ...) }}` in models.
  Analyses use full table names so they paste into the BigQuery console, and return aggregates
  only, never pupil-level rows.
- Every model has a yml entry with a description, the grain in words, and tests on its key.
  Don't add tests that repeat another test or the fetch script's seed validation; test where
  data enters (staging keys), where logic can break, and the app table's contract.
- snake_case; IDs end `_id`, dates `_date`, timestamps `_at`.

## Design rules
1. **Re-runnable.** No `CURRENT_DATE()` / `CURRENT_TIMESTAMP()` / `RAND()` in logic. Every
   `ROW_NUMBER()` has a deterministic order. A full refresh and an incremental run must give
   identical output (checked with `analyses/29_output_checksums.sql`).
2. **Point-in-time** is on `answered_at` (event time; there is no load timestamp). `var('as_at')`
   limits the responses added up in `pupil_subject_year_scores`. There is no day-by-day history table.
3. **Scale.** `trf_pupil_subject_daily` is the only model over the large `responses` table:
   incremental, `insert_overwrite` on `answered_date` day partitions, recomputing the last
   `lookback_days` (3). Staging is views; the raw table isn't partitioned, so each run still scans
   it once (an incremental staging copy would scan the same and add a table to keep in step).
4. **App-DB friendly.** Flat columns, Postgres-compatible types, a **long** app table keyed
   `(pupil_id, subject_name)`: one row per pupil × subject with responses, no row = no score yet.
5. **Scoring is data.** STA tables and the subject → KS2 test mapping live in seeds; never
   hard-code thresholds or subject names in SQL.

## Scope (which responses count)
A response counts when its sitting **exists** (1,433 responses in 56 missing sittings are
excluded), isn't deleted, belongs to a non-deleted pupil, has style `fixed_question` or
`non_adaptive`, and **the pupil's key stage at the sitting matches the assessment's**
(`trf_assessment_key_stage`: the key stage of most of its sittings, tie = KS2). Adaptive is excluded (difficulty tuned to the pupil, so % correct stops measuring
ability; scoring it needs IRT). Surveys have no right answers, which removes Wellbeing. No
`session_type` filter: only summative sittings have responses, and `responses.session_type` is a
constant `MOCK_TEST`. No year-group filter. Incomplete sittings count. Skipped questions count as
answered and wrong (`is_correct` is always false when skipped). **Repeated rows for one question
in a sitting are all kept**, each as a mark; they look like duplicates (FINDINGS 21, 25–28) and
are logged in the README as an identified issue.

## Scoring
- **Per pupil × subject × year group** (of the sitting), add up responses up to `as_at`:
  `percent_correct = 100 × n_correct / n_answered`. The app table keeps each pupil × subject's
  latest year group. **Each key stage uses its own STA tables**: KS1 (Years 1–2) 85–115, KS2
  (3–6) 80–120; `key_stage` is output with every score.
- **Scaled score (Maths, English)**: join `trf_percent_to_scaled_score` on
  - the pupil's key stage at the sitting;
  - the academic year (Sep–Aug) of the latest response: `EXTRACT(YEAR FROM d) - IF(EXTRACT(MONTH
    FROM d) < 9, 1, 0)`, so Sep 2025 – Aug 2026 uses the 2025 table, which STA published in July
    2025. Calendar year would need a table before it's published;
  - the subject;
  - `percent_correct` rounded down to a whole percent.

  The test `assert_scored_subjects_have_scaled_scores` fails if a year has no table.
- **The lookup**: per key stage × conversion year × subject × percent 0–100, equivalent raw =
  `floor(percent × full marks / 100)` on each mapped test → official scaled score → weighted
  average (English = ½ reading + ½ GPS at both key stages), rounded. Raw 0–2 has no official
  score: count it as the scale's bottom (`min_scaled_score`: KS1 85, KS2 80).
- **Other subjects** (Screeners, Verbal / Non-Verbal Reasoning) get % correct only (null
  `scaled_score`). Science has no responses yet, so no rows.

**Conversion tables:** KS1 and KS2 for 2024, 2025 and 2026 are loaded (data needs 2025 and 2026).
To add one once STA publishes it (KS1 June, KS2 July):
`uv run python scripts/build_conversion_seed.py <ks1|ks2> <year>`. It fetches from the GOV.UK
Content API, checks the table (all three tests, raw 0 to full marks, scores non-decreasing across
the scale), prints the raw mark for the expected standard, writes the year
seed, saves the page to `ai/sources/` and regenerates the union model. Never hand-edit the
seeds or the generated model. GOV.UK no longer hosts 2023 or earlier.

| test | KS1 full marks | KS1 expected (2026) | KS2 full marks | KS2 expected (2026) |
|---|---|---|---|---|
| gps | 40 | 24 | 70 | 34 |
| reading | 40 | 29 | 50 | 25 |
| maths | 60 | 36 | 110 | 56 |

## Source tables (`atom-analytics-candidates.de_raw`, profiled 2026-10-20)
All columns are NULLABLE in the schema; profiling results are in `analyses/FINDINGS.md`.
- **`responses`** (63,707 rows; expected 100m+): `response_id` PK; `pupil_id`, `session_id`,
  `question_id`; `is_correct` (never null), `is_no_attempt`, `seconds_taken`, `question_number`,
  `answered_at` (2025-11-10 → 2026-09-16). `session_type` is always `MOCK_TEST` (unused).
- **`assessment_sittings`** (2,509): `session_id` PK; `pupil_id`, `assessment_id`,
  `session_type`, `style` (`fixed_question` / `non_adaptive` / `adaptive` / `survey`),
  `year_group_at_sitting` (1–6, plus 11 / 14 / 15 on entrance exams with no responses),
  `total_questions`, `is_complete`, `is_deleted` (none), `started_at` / `finished_at` (unused).
- **`pupils`** (242, 61 with no sittings): `pupil_id`, `is_deleted` (none). No demographics.
- **`course_hierarchy`** (10,552): `question_id` PK → atom → subtopic → topic → `subject_name`
  (IDs only, no names). One subject per question. Subjects: Maths, English, Science (no
  responses), Verbal / Non-Verbal Reasoning, Wellbeing, Screeners. No validity dates, so treat it
  as current state.

## Profiling and analyses
Write one query per question as `analyses/NN_<topic>.sql` with a header comment (what it checks,
why it matters). Run with `uv run python scripts/run_analyses.py` (dry run) and `--run [prefixes]`
(saves `analyses/results/<name>.csv`), **with the user's permission**. Record results, decisions
and affected rows in `analyses/FINDINGS.md`, written for a reviewer. Queries 29–31 verify the
built models (checksums, hand check, distribution).
