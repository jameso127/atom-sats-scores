## 2026-10-20: repo setup
- **Conversion seed script now fetches from GOV.UK.** Previously it parsed a saved page. It reads
  the GOV.UK Content API (JSON wrapping the page HTML) for "Key stage 2 tests: <year> scaled
  scores", validates each table, and merges by year. Re-fetching 2024–2026 matched the
  hand-transcribed seed row-for-row. The 2024 page groups raw marks "0 - 2" into one row, so the
  parser expands ranges. GOV.UK returns 404 for 2023.
- **Seed files were swapped.** `seed_ks2_scaled_score_conversion.csv` held the subject mapping and
  `_seeds.yml` held the conversion table. Moved the mapping to `seeds/seed_subject_to_ks2_test.csv`,
  regenerated the conversion seed with the script, and made `_seeds.yml` a real properties file.
- **uv for Python.** `pyproject.toml` + `uv.lock` pin dbt-core 1.12.6 / dbt-bigquery 1.12.1 on
  Python 3.12. dbt v2 exists, but the brief and CLAUDE.md specify dbt Core.
- **Seed tests as singular tests** in `tests/`: weights sum to 1 per subject, all three tests per
  conversion year, monotonic conversion tables.
- **No source tests on `responses`**: they would full-scan a table expected to exceed 100m rows.

## 2026-10-20: conversion table chosen by academic year, per score
- **Was:** one table per build, the latest published on or before `as_at`; older scores were
  converted with the build's table.
- **Now:** each history row uses the table for the academic year (Sep–Aug) of its `valid_from`;
  Sep 2025 – Aug 2026 uses the 2025 table (published July 2025). Proposed by the user, who suggested
  calendar or Sep–Sep years; academic year was chosen because a calendar-year rule needs the 2026
  table from January 2026, months before STA publishes it, so scores would fall back and later be
  silently rescored.
- The table is chosen per score, not per response, because responses are pooled into one % correct.
- `published_date` stays in the seed for provenance but no longer drives the choice.

## 2026-10-20: one seed per conversion year

## 2026-10-21: percent → scaled score lookup (user's idea)
- User suggested holding scaled scores against percentages in a table and joining to it.
  Added `trf_percent_to_scaled_score` (conversion year × subject × whole percent 0-100, English
  blended), built from the seeds with generate_array(0, 100). The year model is now one CTE and a
  single left join on (academic year, subject, whole percent); no raw-mark arithmetic or weighted
  average there. Non-mapped subjects simply find no lookup row.
- Trade-off: whole percents are coarser than raw marks (Maths 1% ≈ 1.1 marks), so a score can be
  ~1 point lower near a boundary; 0.1% steps would be a one-number change.
- pct_correct (0-1) renamed percent_correct (0-100). New test `assert_lookup_has_every_percent`.
  Hand check (30) updated to the whole-percent method.
- Not built yet.
